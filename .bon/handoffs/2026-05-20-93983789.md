## For Claudes to come

When you're about to scrape more than a couple of pages from a modern docs site — Angular, React, Vue, or any SPA where content is rendered client-side — the rendering layer is *never* the authoritative source. The site fetches its own data, usually as `.md` or `.json`, and renders it. That source is one network capture away: `passe capture --bodies` on a single page load, then grep the response URLs for `/assets/`, `/api/`, or `/docs/` paths returning markdown or JSON.

This worked example (Antigravity, 2026-05-20) showed the cost of skipping the check: ~30 minutes burned across three extraction approaches (Devdocs API, passe fetch / trafilatura, custom DOM walker), with the trafilatura path producing files that *looked* complete but had every code block silently stripped because `<app-code-snippet>`'s `<code>` elements were empty in the DOM. Five minutes after running `passe capture --bodies`, 58 files came down from `/assets/docs/<section>/<page>.md` byte-perfect with frontmatter, code fences, language hints, and image refs intact.

The principle generalises beyond docs: any time a rendering layer sits between you and structured content, ask "where does this data come from?" before extracting from the render. The render is downstream; the source is upstream; upstream is always strictly better. This is the same family as the `WRITE_*`/`DUMP_*` env-var grep pattern and the gemini-cli `isSectionEnabled` discovery — cheap source-discovery moves that prevent structural rework. Self.md verification discipline #14 (substrate-first design) has the principle; today's new entry under Workflow patterns names the docs-SPA-specific activator and corrective.

The activator next time should be concrete: **JS-rendered docs site + planning to scrape >3 pages = `passe capture --bodies` on page one before anything else.**
